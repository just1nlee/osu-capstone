# MediaPipe tmux Companion Implementation Plan

> Historical implementation milestones. For the current model setup and runtime, see the [MediaPipe guide](docs/MEDIAPIPE_RECOGNITION.md).

**Goal.** Build a standalone macOS Electron companion that recognizes hand gestures in the background and runs commands against an existing local tmux session.

**Architecture.** One Electron renderer owns the camera, MediaPipe, the gesture state machine, and the two-panel UI. Electron's main process owns session discovery, saved mappings, dispatch validation, and short-lived `execFile` calls to tmux. The user's usual terminal runs its own tmux client.

**Stack.** Reuse the prototype's JavaScript, npm, Electron 45.1.0, and `@mediapipe/tasks-vision` 0.10.35 with the same float16 model. Use Node.js 22.12 or later for tooling and tmux 3.5a as the first verified baseline. Run from source with `npm ci` and `npm start`.

## Scope and sources

- The companion lives in `playground/mediapipe_tmux_companion` in this repository. It reuses recognition techniques from the [original MediaPipe example](../mediapipe-example/MEDIAPIPE_INTEGRATION.md).
- This prototype follows the capstone's goals of keeping the existing terminal and making the camera optional (FR-10/11), providing gesture diagnostics (FR-14), and persisting remaps (FR-15). It uses tmux, Electron-owned recognition, and CLI dispatch. The accepted capstone ADR describes a C multiplexer with a separate headless recognizer and local socket intents. The product toggle owner remains proposed. The full command catalog and frame-count stabilization are prototype behavior. [ADR-0001](https://github.com/just1nlee/osu-capstone/blob/5b6f3e8/docs/adr/0001-hybrid-multiplexer-architecture.md), [ADR-0002](https://github.com/just1nlee/osu-capstone/blob/5b6f3e8/docs/adr/0002-recognition-toggle-owner.md), [requirements](https://github.com/just1nlee/osu-capstone/blob/5b6f3e8/docs/requirements.md), [design](https://github.com/just1nlee/osu-capstone/blob/5b6f3e8/docs/design.md)
- The app uses a local tmux CLI and user-owned server. The scope excludes an embedded terminal, PTY, xterm.js, control mode, shell I/O, command stdout display, HTTP, gesture-related keyboard bindings, key recording, and automatic tmux configuration. A manually configured gesture may still invoke a tmux command whose own effect is to alter sessions or keys. Closing the companion never issues a tmux cleanup command.
- Camera frames and diagnostics stay in memory on the device. Ship the matching WASM with the local model setup, allow only video from the trusted renderer, and keep tests free of saved camera frames. Release packaging and installation at login are outside this plan.

## User flow and defaults

```text
tmux session [ work ▾ ]  [Refresh sessions]     Camera off [Turn camera on]
┌───────────────────────────────┬──────────────────────────────────────────┐
│ MediaPipe                     │ Gesture mappings                         │
│ Preview and pose diagnostics  │ Thumb Up   [Move pane ▾]       [Enabled] │
│ Confidence and gate state     │   Destination [Next pane ▾]              │
│ Recognition sliders          │ Victory    [No command ▾]     [Disabled] │
│ Full result and decision log  │ …one row for each supported gesture…     │
│                               │ [ ] Allow closing and guarded commands  │
│                               │ [Save mappings]                          │
└───────────────────────────────┴──────────────────────────────────────────┘
```

- Show the window at launch. Keep both panels visible side by side at normal desktop widths, with independent scroll areas and a stacked layout when narrow. Keep the session picker and camera status in the header.
- Discover sessions on one server. Default to tmux's normal socket. For a named server such as `gesturemux-prototype`, allow a startup override using `TMUX_COMPANION_SOCKET_NAME` for `-L` or `TMUX_COMPANION_SOCKET_PATH` for `-S`. Reject both set together. Include detached sessions and label attached state. Selecting a session sets the destination for commands without creating a terminal client.
- On launch, select the only session automatically. With two or more, leave the dropdown on **Select a session**. With zero, show **No tmux sessions found** and keep **Refresh sessions** available. Manual refresh repeats discovery even when the app opened first. While a session is selected, refresh at a three-second interval to detect loss. Preserve the same selection on rename or if new sessions appear. If the selected session or server disappears, pause dispatch and require an explicit selection, even if one session remains.
- Start the camera off. A menu-bar item shows camera state and offers **Open Companion**, **Turn camera on/off**, **Refresh sessions**, and **Quit**. Closing the window hides it. Camera recognition continues when enabled and sends gestures to the selected session even while a terminal is focused. With no selected session, the enabled camera supports diagnostics and gesture actions are paused. Screen lock, sleep, renderer loss, and quit stop capture and cancel pending actions. Camera restart after waking or unlocking is manual.
- Render one fixed row for each of `Closed_Fist`, `Open_Palm`, `Pointing_Up`, `Thumb_Down`, `Thumb_Up`, `Victory`, and `ILoveYou`. The model reports 21 landmarks per hand and seven assignable poses. Each row has **No command** plus the installed tmux command catalog, an enable checkbox, any applicable options, and a validation message. All rows start unassigned and disabled. The first command chosen for a row enables it. Disabling retains the selected command and its options. Clearing the command resets the row. Multiple gestures may use the same command. Only saved, enabled rows dispatch.
- Keep **Allow closing and guarded commands** off at app launch. It remains checked until the user unchecks it or quits. A guarded gesture requires a one-second continuous hold after stabilization, even when ordinary gesture cooldown is set to zero. Changes to target, relevant mapping, camera eligibility, or guard state cancel an in-progress hold. A pose already held while an action becomes eligible must be released before it can fire.
- Preserve the preview, label and confidence, handedness, landmarks, full MediaPipe result, frame and inference timing, state, last action, freeze, clear log, and bounded decision history from the full prototype. Keep the sliders at 5 FPS (1–30), 0.70 confidence (0.50–0.95 in 0.05 steps), two consecutive frames (1–10), and 1,000 ms cooldown (0–3,000 in 100 ms steps). Slider values reset on restart. Freeze affects the displayed result. Inference and history continue.

| `electron/settings.cjs` | Atomic reads and writes of the companion's own gesture mappings |
| `electron/dispatch.cjs` | Main-process permission, timing, target and mapping checks, outcomes, and command invocation |
| `shared/config.js`, `shared/commands.js` | Gesture schema, validation, known command profiles, option fields and execution planning |
| `renderer/index.html`, `renderer/style.css`, `renderer/main.js` | Main window, session UI, camera status and composition |
| `renderer/gestures.js`, `renderer/gesture-gate.js`, `renderer/debug.js`, `renderer/settings.js` | Reused capture, stabilization and diagnostics, plus per-gesture editing |
| `tests/session.test.cjs`, `tests/tmux.integration.test.cjs`, `tests/config.test.mjs`, `tests/commands.test.mjs`, `tests/gesture-gate.test.mjs`, `tests/dispatch.test.cjs`, `tests/app.test.cjs` | Unit, isolated tmux integration, and Electron smoke coverage |

Use a distinct Electron application name and user-data directory. Store `gesture-mappings.v1.json` there with `{ version: 1, gestures: { [label]: { enabled, binding } } }`. Each of the seven keys is required. `binding` is null or `{ command, mode, options, args }`. `mode` is `guided` or `advanced`. `options` holds typed, profile-validated values such as `{ destination: "next-pane" }`. `args` is a bounded string array (up to 32 values, up to 512 characters per value, no NUL). A disabled row may keep a valid binding. A command removed by a tmux upgrade stays visible in saved settings but cannot dispatch until restored or changed. Save uses a serialized temp-write-and-rename and publishes the new mapping revision only on success.

Use the preload namespace `window.gestureCompanion`. Each method below uses the exact channel shown. Invoke results are `{ ok: true, ...data }` or `{ ok: false, code, message }`. Events return unsubscribe functions from preload.

| Channel | Direction and payload |
| --- | --- |
| `companion:getState` | Renderer invokes with no payload. Returns the snapshot and saved mappings with revision. |
| `companion:refreshSessions` | Renderer invokes with no payload. Returns new session state. |
| `companion:selectSession` | Renderer invokes with opaque `sessionKey`. Returns new session state. |
| `companion:listCommands` | Renderer invokes with no payload. Returns `commands: [{ name, usage }]` or an actionable catalog error. |
| `companion:saveMappings` | Renderer invokes with complete settings object. Returns normalized mappings and revision. |
| `companion:checkMapping` | Renderer invokes with `{ gesture, binding, targetToken }`. Returns a target summary or error using read-only resolution. |
| `companion:setCameraEnabled` | Renderer invokes with boolean. Main owns the requested state and capture generation. |
| `companion:reportCameraStatus` | Renderer invokes with `{ captureGeneration, phase }`. Main only accepts reports for the active generation. |
| `companion:setGuardUnlocked` | Renderer invokes with boolean. Returns current checkbox state. |
| `companion:dispatchGesture` | Renderer invokes with `{ gesture, revision, targetToken, captureGeneration, phase?, holdId? }`. Main resolves the saved binding itself. |
| `companion:stateChanged` | Main pushes changes to the state snapshot, including window visibility. |

The snapshot contains `sessions` (`status`, list of `{ key, name, attachedClients }`, `selectedKey`, `targetToken`), `camera` (`enabled`, `captureGeneration`, `phase`), `guardUnlocked`, `windowVisible`, and `sequence`. Camera phases are `off`, `starting`, `loading`, `on`, and `error`. Dispatch phases are `begin`, `commit`, and `cancel` for guarded commands. Omit the phase for ordinary commands. Subscribe before the initial state read and apply snapshots in sequence order. Validate the caller against the single trusted main frame. Reject navigation, new windows, microphone permission and arbitrary process access. The renderer sends pose labels and control state through IPC. Preview frames and raw MediaPipe results stay in the renderer.

## How a command becomes runnable

1. **Get the catalog from the running tmux server.** Query `tmux -N … list-commands -F '#{command_list_name}<TAB>#{command_list_usage}'`, with a literal tab in the format. Separate catalog availability from session availability. With no server, keep saved mappings available and explain that starting tmux and refreshing will make the catalog available. Cache a successful catalog for editing until refresh, and invalidate it for dispatch when the server identity changes. tmux 3.5a was checked locally. Plain `list-commands` can start a server, while `-N` keeps the probe from doing so. [tmux manual for 3.5a](https://github.com/tmux/tmux/blob/3.5a/tmux.1)
2. **Use command-specific defaults and guided fields.** In `shared/commands.js` expose `getCommandForm(metadata, binding)` and `prepareCommand(metadata, binding, context)`. Preparation returns exact argv, a readable destination summary, and the guard classification, or a specific validation code. Give `select-pane` a no-argument next-pane default, use the selected active pane for `split-window` and layout actions, and ask for a new name for `rename-window`. For other commands show usage and infer only unambiguous fields. Brackets in tmux usage describe CLI syntax. They cannot tell the app when a pair of targets or a live client is needed.
3. **Give `move-pane` and `join-pane` a real target picker.** For the standard pane move, source defaults to the selected session's active pane. Require a **Destination** choice of **Next pane in this window**, **Next window's active pane**, or **Previous window's active pane**. Resolve relative choices each time by numeric pane or window index, wrapping within the selected session. Pass both `-s` and `-t` as explicit stable targets. Report **Choose a different destination pane**, **This window needs a second pane**, or **This session needs a second window** as appropriate. Verify a distinct pane ID. tmux 3.5a accepts distinct panes in one window and across windows. Bare `move-pane` reproduced `source and target panes must be different` on a disposable server. The full prototype's generic adapter neither prepares the source nor handles the `dst-pane` usage token. [tmux 3.5a implementation](https://github.com/tmux/tmux/blob/3.5a/cmd-join-pane.c)
4. **Support the full catalog with an Advanced options path.** Show literal argv one argument per line and tmux's live usage for commands that need other values or modes. Do not interpret the text as a shell command. Recognize combined short flags, attached values, separate values, and the `--` delimiter when detecting explicit targets. For a known multi-target command in advanced mode, require explicitly supplied targets when the requested mode needs them. Where tmux exposes an unambiguous target flag and no explicit value was supplied, bind it to the selected session's scoped window, pane, or eligible client. Treat contextual destinations such as a new window slot separately. For a target form the adapter cannot infer, request explicit values. Label explicit overrides and server-wide commands in the UI. For commands needing an attached client, choose an implicit client only when exactly one client is in the selected session. With zero or several, give a client-specific message or require an explicit client as supported by that command. Commands needing a real interactive TTY can still be selected, but show that they must be run from a terminal if tmux rejects headless invocation. The command catalog is broader than the set of operations that can run with no TTY.
5. **Check without executing, then validate again on dispatch.** The mapping row has **Check settings** for commands with required options or targets. It resolves the live target and builds the same argv as dispatch without invoking the action. A successful check confirms known prerequisites. tmux remains responsible for accepting the final command and can reject it as layout, version, options, or client state changes. Retain a bounded plain-text error summary from stderr in memory and show it alongside the affected gesture in the diagnostic log. Distinguish missing input, unavailable command, missing or ambiguous target, guard lock, interactive-only command, timeout, and other tmux failures. For an unknown failure show the first bounded, control-character-stripped diagnostic line. Do not render action stdout, terminal contents, or raw argv.

## Handoff criteria

The acceptance run covers the late-start/no-session flow, one-session auto-selection, a dropdown for multiple sessions, and a session ending while a pose is held. A configured gesture runs in the selected tmux session while the companion window is hidden. The same window shows MediaPipe diagnostics next to all seven mapping rows. A row retains its command while disabled. A known missing prerequisite appears as a specific message before execution, and unknown tmux errors include a readable cause. The usage guide explains launch, the named-socket override, camera control, how to map and check a command, which commands require a hold, and how to verify a command in a disposable session.


## Verification record

Verified normal startup with a disposable session on macOS, the seven-row layout, and camera off at launch. The integration suites exercise tmux 3.5a and 3.8. The Electron smoke test exercises generated video, the Chromium fake camera through Electron's media permission handlers, and a synthetic label flowing through the real gesture state machine to a real tmux client attached to a test PTY. The physical webcam and recognition of a real hand remain to be verified manually.

The model is now read from the repository’s ignored `test-model/models/gesture_recognizer.task` file. Unit tests verify the shared model route, and the Electron smoke test compares the served bytes with the file on disk. See [shared model setup](docs/MEDIAPIPE_RECOGNITION.md).
